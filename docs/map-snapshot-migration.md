# ゲーム別固定マップSnapshotの導入

## 保存形式と移行

`game_map`を追加する。game_idはplayer_status.idを参照する主キー、
schema_versionは1、sourceはfixedまたはlegacy-fixed、definitionはJSON。
player_status、node_status、ログ、既存テーブルの列は変更・削除しない。
新規ゲームとSnapshotの作成は同じトランザクションで行う。

現在のプロジェクトの`Base.metadata.create_all`による起動時移行を使用する。
新しいmain起動時に不足テーブルだけ作成し、NodeMaster同期前にSnapshotがない
既存ゲームを補完する。追加SQLを手動実行したりDBを初期化する必要はない。
起動時に一括補完できなかった旧ゲームも取得時に補完できる。
再実行しても保存済みSnapshotを再作成しない。

旧ゲームの座標・説明は同期前のNodeMasterから採る。接続・ルールは過去版の保存が
存在しなかったため移行時の固定値になる。この制約を隠して完全復元とは扱わない。
非対応版や破損Snapshotは409で止め、自動修復で進行やマップを失わせない。
保存済みマップが参照するNodeMasterを起動時掃除から保護し、
既存の古いゲーム削除処理では対応するSnapshotも削除する。

## 導入と確認

1. 既存DBをバックアップし、まず隔離DBで起動する。既存ボリュームを削除しない。
2. 新規Stage1のGameStateで24ノード・38接続とmapSnapshotを確認する。
3. 進行後にBackend再起動・ブラウザ再読み込みを行いgameIdと進行・接続・座標が維持されることを確認する。
4. RETRYでノード進行・時間・資源が初期化され、保存定義は維持されることを確認する。
5. 旧ゲームの進行と移行前座標が保持され、sourceがlegacy-fixedになることを確認する。

Mockの保存先はブラウザlocalStorage。ブラウザデータ削除/別ブラウザでは引き継がれない。
古い形式・非対応版・破損したMock保存は対象ゲームのキーだけを削除し、新規初期状態で再開する。
復旧したことはゲーム内ログに表示し、HTTP保存や他ゲームには影響させない。
保存容量不足時は操作の結果を成功扱いせず、最後に保存された状態を保持する。
既存Mockには進行保存がなかったため、保存情報がない旧gameIdは従来どおり固定初期状態で開始する。

## 今回の範囲と次段階

固定0/1/2の定義をゲームごとに凍結する。Stage1の24ノード・38接続・座標、
全45ノード135問・ギミックの生成元は変更しない。
RETRYは同盤面、新規gameIdは新しい定義を保存する。今は固定なので新規でも同じ盤面になる。
ランダム生成器、シード発行/UI、探索・難易度保証は次段階。
既存Stage3は未実装のため新たな動作は追加しない。
将来generatorVersion/rulesVersionを変える際は、古い保存版を読めるデコーダーと
明示的な移行方針を先に追加する。
